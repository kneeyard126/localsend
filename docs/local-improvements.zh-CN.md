# LocalSend 本地改进记录

调研日期：2026-11-20。源码基线：`8e999736643547a3b375e1d442d160fa852db6ef`。
官方安装包：v1.18.2；源码使用当前 main，不能把这个本地构建称为官方 v1.18.2 发布版。

## 判断

LocalSend 适合做跨平台局域网传输的基础。现成的设备身份、设备发现、HTTPS 和文件传输可以保留。
用户希望的“像聊天一样互传”也有明确的社区需求，但属于独立的产品工作，不能声称修两个 bug 就已经实现。

## 第一轮已修改的代码

| 问题 | 原因与改进 | 范围 |
| --- | --- | --- |
| 长剪贴板文字可能使接收端卡顿 | 发送端原先把完整文本嵌入 preview，接收端作为一个可选择段落排版。现在内联消息限定为 16 KiB UTF-8；超出后仍通过原协议发送完整 `.txt` 文件，不截断正文。接收端也检查旧版本发来的 preview，不能只信文件大小。 | 对应 [#2830](https://github.com/localsend/localsend/issues/2830)、[#2862](https://github.com/localsend/localsend/issues/2862) 所报告的路径；测试验证边界行为，未声称已在报告中的 Android/Windows 实机复现内存峰值。 |
| 复制文件却发送成路径文字或图片缩略图 | 剪贴板读取顺序改为“文件 → 文字 → 图片”。不支持文件剪贴板的平台继续回退到文字/图片。 | 解决 [#3478](https://github.com/localsend/localsend/issues/3478) 的格式优先级部分。该 issue 的锁定键问题在下载的源码中已有 `SingleActivator` 修复；Wayland 底层读取失败仍需另行验证。 |
| 浏览器分享时附件预览错配 | 每个附件使用自己的预览，不再把第一项的文字预览重复赋给所有附件；同时使用同一文本大小限制。 | 源码检查发现，属于同一路径的修复。 |
| 空文件集合读取消息会异常 | 先检查集合长度，空请求返回无消息。 | 增加回归测试。 |

选择列表也应用同一限制，避免为了显示一行文字而解码和排版整份大文本；短消息仍可编辑。
HTTP 接收、WebRTC 接收界面和浏览器分享使用相同的边界规则。
本次没有更改传输协议、证书校验、PIN 或接收确认策略。

## 聊天式版本的建议

桌面端采用设备列表和会话区；手机端先选设备再进入会话。文本、链接、文件及传输进度统一展示。
常用操作是粘贴、拖拽、复制与下载，连接故障应直接显示可操作的原因。

会话按证书指纹识别设备，历史同时包含发送与接收事件。接收文件成功落盘后才标记完成，失败时保留重试入口。
历史保留期限与自动接受都由用户控制，初次来访设备沿用接收确认。
当前核心一次只允许一个上传会话；做连续聊天时，需要单独处理消息队列和并发，而不是简单隐藏确认窗口。

建议顺序：可靠传输基础 → 双向历史 → 单设备会话 → 多设备会话 → 后台与断点恢复。
以上是后续设计，第一轮补丁尚未实现聊天、群聊或断点续传。

## 验证命令

在 `app/` 中，按仓库 `.fvmrc` 使用 Flutter 3.41.9：

```sh
fvm flutter pub get
fvm flutter analyze --no-pub
fvm flutter test --no-pub
fvm dart format --set-exit-if-changed lib test
```

新回归测试覆盖剪贴板文件/文本/图片优先级、缺失插件回退、UTF-8 边界、旧端大预览、空请求，以及发送请求中的预览和原始内容是否独立保留。
选择列表另外验证短文本可编辑、长文本按文件展示。

本轮验证结果：

- `flutter analyze --no-pub`：无问题。
- `flutter test --no-pub`：126 项全部通过。
- 所有修改的 Dart 文件通过格式检查，`git diff --check` 通过。
- Apple Silicon macOS release 构建成功，已启动并查看界面。
- 本机真实 HTTPS 双向证书连接验证：36 字节中英文短消息正常显示并可复制；模拟旧端携带 111000 字节完整 preview 的长文本进入文件接收流程，接收完成。
- 收到的长文本为 111000 字节，SHA-256 为 `5de4f76b736ee9c60ea33ac6a692269ba30f85336eb1e0ed51c7bce81d50a88a`，与发送内容一致。

这是本机回环协议验证，不等同于 Mac↔Windows 或手机实机验证，也没有重现 issue 中提到的 11 GB 内存峰值。

macOS 本地构建需要完整 Xcode。仓库的开发者签名团队属于上游；个人本地构建应使用自己的签名设置或临时关闭构建签名并进行本地 ad-hoc 签名，不修改全机安全设置。
Windows、Android、iOS 的实机兼容性不等同于 macOS 构建成功，需要各平台继续验证。
随附的 Mac 应用使用本地 ad-hoc 签名，保留主应用沙盒和原有文件/网络权限，不带上游开发者团队的 App Group 授权；系统分享扩展尚未验证。它不是经过上游签名与公证的安装包。

所有改动只在本地仓库，未向上游发布 issue、评论或 PR。
